# Mahjong レビュー報告 2026-09-10

## 対象

- `Mahjong/` の牌・面子・待ち探索・直接生成・待ち分解コード
- `MahjongComputations/` の共通集計と4枚形レポート
- `MahjongTests/` の回帰テスト
- Mahjong 関連の設計・語彙・レビュー文書

## 総評

Mahjong 本体、テスト、4枚形レポート生成は次のコマンドで成功した。

- `lake build Mahjong`
- `lake build MahjongTests`
- `lake build fourTileReport`

探索の健全性・完全性を外延仕様へ接続する定理があり、`sorry` に依存した未完成箇所も確認できなかった。一方、レポート分類に使う値の情報量と、可約性の変更後の期待値については、結果利用者が誤解しないよう仕様を確定させる余地がある。

## 所見

### 1. 待ち分解コード列が待ち牌ごとの多重度を失う

重要度: 中

`waitDecompositionCodes` は `waitDecompositionCodeEntries` のコードを取り出した後、`deduplicateAndSortBy id` で重複を除く。[WaitDecompositionCode.lean](../Mahjong/WaitDecompositionCode.lean#L350-L380) の例でも、`2345678m` の3待ちがすべてコード `338` であるにもかかわらず、結果は `[338]` になることを仕様として固定している。

これは集合として分類する用途なら正しいが、待ち分解の件数、待ち牌ごとの対応、同一コードが何回現れたかを必要とする用途では情報を復元できない。`FourTile` のレポートもこの値をそのまま `waitDecompositionCodes` として保存しているため、出力の `[338]` は「3待ちが同じコードだった」のか「コードが1件だけ存在した」のかを表現できない。

既存の [review-backlog.md](review-backlog.md#L120-L155) でも認識済みだが、現状は設計判断が未完了である。

推奨対応:

- 多重度を保持する `waitDecompositionCodes` と、集合化した派生 API を分離する。
- 少なくとも API コメントとレポート仕様に「待ち牌を忘れた後の重複を除く」ことを明記する。
- 変更時は `2345678m` の期待値を `[338, 338, 338]` とするテストを追加し、4枚形・7枚形の集計値を再生成する。

### 2. 可約性分類の変更後の代表例・集計差分が仕様確認待ち

重要度: 中

現行の4枚形レポートは、`enumeratedDerivations: 5100`、`tenpaiReports: 3756`、可約 `1647`、既約 `2109` となっている。[FourTile.lean](../MahjongComputations/FourTile.lean#L20-L55) では、レポートの可約性を `determineReducibility` に委ねている。[WaitDecompositionCode.lean](../Mahjong/WaitDecompositionCode.lean#L382-L425) では、完成面子を除いた残りについて待ち核集合を比較して可約性を決める。

この定義自体はコードと証明の接続が明確だが、実装変更後に `1223m`、`1233m` などが既約側へ移った理由と、旧分類との差分が期待どおりかは、[review-backlog.md](review-backlog.md#L157-L180) に保留として残っている。ここを未確定のまま集計値だけを回帰値にすると、意図した仕様変更と回帰バグを区別しにくい。

推奨対応:

- `1223m`、`1233m` を最小の仕様例として、待ち核と可約性の期待値をテストへ固定する。
- 「可約」は完成面子の除去後も同じ待ち核集合を保つこと、という定義をレポート README からも参照できるようにする。
- 旧レポートとの差分を仕様変更として採用するか、旧分類を正しいとするかを決定し、決定理由をバックログから完了項目へ移す。

### 3. 列挙・重複除去の公開不変条件が型・定理で十分に固定されていない

重要度: 低

`waitDecompositionCodeEntries`、`waitDecompositionCodes`、`groupWaitCompletions` は、並び順や重複除去を計算処理として実装している。一方、利用側が依存する `Nodup`、ソート順、同一牌姿内のグループ一意性を直接示す公開定理は限定的である。[Common.lean](../MahjongComputations/Common.lean#L35-L90) のグループ化も、牌姿キーでソートされた入力を隣接走査する実装になっている。

現状のビルドでは問題は発生していない。ただし、重複除去やソート処理を変更しても、レポートの前提を破ったことがコンパイル時に検出されない。特にコード列の多重度を見直す際には、既存の集計が意図せず変わるリスクがある。

推奨対応:

- 公開 API として重要なものに `Nodup`、ソート、グループキー一致の補題を追加する。
- 多重度を保持する仕様へ変更する場合、集合版が単なる射影であることを補題で示す。
- まずは既存の具体例を保った小さな定理から追加し、抽象的な探索 API は増やさない。

## テスト上の不足

- `DirectWaitGeneration.hand` と `completion` の中間結果を直接確認する例が少なく、現在は主に大量の件数と Finder との接続で検証している。[DirectWaitGeneration.lean](../Mahjong/DirectWaitGeneration.lean#L560-L650)
- `MahjongComputations.Common` の合法多重集合列挙、グループ化、集計について、境界値の小さな例が少ない。
- ただし、今回確認した範囲でテスト失敗やビルド警告はなかった。ここは直ちに不具合と断定する項目ではなく、将来の仕様変更に対する回帰検出力の課題である。

## 対応優先順位

1. `waitDecompositionCodes` の集合／多重集合の仕様を確定する。
2. `1223m`、`1233m` を含む可約性の最小仕様例を追加し、現行レポートの差分を承認または修正する。
3. レポート集計が依存する重複除去・グループ化の不変条件を補題で固定する。
4. 直接生成と共通集計の中間結果に、少数の具体例テストを追加する。

## 結論

重大な実装破壊やビルド不成立は確認されなかった。優先して扱うべきなのは、`waitDecompositionCodes` が意図的に失っている多重度をレポート利用者へ明確に伝えることと、可約性分類の変更後の期待値を仕様として確定することである。
