# 13枚形レポート生成：軽量シャード化案 2026-09-11

## 背景と動機

前の完全なシャード化設計は、導出ファイル・マニフェスト・`.done` マーカーなど複雑な状態管理が必要でした。
一方、チェックポイント方式は実装は簡単（100～150行）ですが、メモリ内のハッシュマップが生成終了まで
増え続けるため、OOMリスク（8GBコンテナで最大8時間の計算が失敗）を根本的には解決しません。

本案は両者の中間：**粗いシャード分割（key % numShards）で、ピークメモリを事前に削減**しつつ、
**チェックポイントなみの実装シンプルさを保つ**折衷案です。

## 目標

1. **ピークメモリ削減**：シャード数 k に対して、ピークメモリを約 1/k に圧縮（同時保持件数が削減）
2. **実装コスト最小化**：完全シャード化（300～500行）より小さい（150～250行）
3. **安全性向上**：各シャードが独立に30分以内で完了する設定を目指す
4. **再開可能性**：シャード k が失敗しても、再実行すれば他のシャードの結果と統合可能

## 実装方針

### 1. シャード分割キー

牌多重集合キーの下位ビットで分割：

```lean
def shardIndex (tiles : List Tile) (numShards : Nat) : Nat :=
  tileMultisetKey tiles % numShards
```

- 分割は排他的（各牌姿はちょうど1シャードに属する）
- 異なるシャード間に重複なし

### 2. シャード数の選定

10枚形の実測から逆算：

- **実測値**：テンパイ形 3,431,439 件、実行時間 1043秒（17分23秒）
- **1件あたり**：0.30秒
- **目標時間**：30分以内で完全に完了

13枚形推定：

| シナリオ | テンパイ形数 | 1件コスト | 13枚形時間 | シャード数 k | 1シャード時間 |
|--------|------------|---------|----------|----------|-----------|
| 楽観的 | 50M | 0.30秒 | 4.2時間 | 8 | 31分 |
| 中心 | 67.5M | 0.30秒 | 5.6時間 | 10 | 34分 |
| 悲観的 | 85M | 0.35秒 | 8.3時間 | 14 | 35分 |

**推奨**：`numShards = 12`（中心値で30分以内、悲観的でも40分以内）

ピークメモリ削減：
$$
\text{ピークメモリ} \approx \frac{2.6 \text{ GB}}{12} \sim \frac{4.4 \text{ GB}}{12} \approx \text{0.22～0.37 GB}
$$

これはメモリの余裕が十分であり、複数シャードの並列処理や再実行も可能になります。

### 3. 処理フロー

```
Step 1: numShards = 12 に対して、shardIndex ∈ {0, 1, ..., 11}
Step 2: 各シャード i に対して処理を実行
        - 牌姿ごとのフォルダ: reports/thirteen-tile-shards/shard-{i}/
        - 出力ファイル: reports/thirteen-tile-shards/shard-{i}/result.txt
Step 3: 全シャード完了後、結果を統合
        - 最終ファイル: reports/thirteen-tile-direct-report.txt
```

### 4. 各シャード処理の実装

`MahjongComputations/ThirteenTile.lean` を改造：

```lean
structure ThirteenTileShardConfig where
  shardIndex : Nat
  numShards : Nat

def computeThirteenTileShard (config : ThirteenTileShardConfig) : IO ThirteenTileReport := do
  let result := canonicalWaitCompletionGroups 4
  let filtered := result.groups.filter fun group =>
    shardIndex (group.tiles) config.numShards == config.shardIndex
  -- filtered に対してレポート集計を行う
  ⟨...⟩
```

### 5. 最終マージ

各シャード結果ファイル（JSONL または テキスト）を順番に読み込んで、
グローバルな集計（テンパイ形総数、可約性グループなど）を再計算：

```lean
def mergeThirteenTileShards (numShards : Nat) : IO ThirteenTileReport := do
  let mut allGroups : List WaitDecompositionCodeGroup := []
  for i in [0 : numShards] do
    let filePath := s!"reports/thirteen-tile-shards/shard-{i}/result.txt"
    let shardResult ← loadThirteenTileShardResult filePath
    allGroups := allGroups ++ shardResult.groups
  -- 統計情報を再計算して最終レポートを生成
  formatThirteenTileReport allGroups
```

### 6. lakefileへの追加

```lean

    }

-- 統合ターゲット

  -- 全シャードの完了を待ち、マージを実行
  ...
```

## キャッシュとシャード分割の関係（重要）

### キャッシュアクセスはシャード内に閉じない

現在のキャッシュ実装では：

- **キャッシュキー** = 縮小後の手牌の `tileMultisetKey`
- **キャッシュ値** = 待ち核集合

しかし、**シャード分割キー** = **元の手牌** の `tileMultisetKey % numShards`

これら2つは独立しているため、キャッシュアクセスはシャード境界を越えます。

**例：**

```
元の手牌 A（shardIndex = 0）から面子 X を除去 → 縮小手牌 B
元の手牌 C（shardIndex = 5）から面子 Y を除去 → 同じ縮小手牌 B

→ シャード 0 の処理とシャード 5 の処理が、
   同じ縮小手牌 B のキャッシュエントリを共有する可能性がある
```

### 設計決定：グローバルキャッシュを保持

本計画では、**各シャードが処理を進める間はグローバルキャッシュを共有し、
シャード処理完了時にキャッシュを破棄**する方針とします。

| 代替案 | 利点 | 欠点 |
|------|------|------|
| **グローバルキャッシュ（採用）** | キャッシュ効率が最高 | 複数シャード並列実行時はロック必要 |
| シャード毎独立キャッシュ | 並列化が簡単 | キャッシュヒット率低下 |

採用理由：
- キャッシュ破棄により、メモリ削減の目的（ピークメモリ = 最後のシャード処理時）は達成
- キャッシュ効率が劣化しない
- 単一ターミナルで順番実行の場合、同期の問題なし

### 実装上の注意

シャード i を処理する時点で、キャッシュ内には前のシャード j (j < i) の
縮小手牌エントリが残っている可能性があります。これは**意図的に許容**します。

（異なる元手牌から同じ縮小手牌へたどり着く場合、そのキャッシュエントリを
再利用することで計算を削減）

ただし、複数シャードを並列実行する場合は、各シャードプロセスに独立した
キャッシュを与える必要があります。

## 懸念点と対策

| 懸念 | 対策 |
|-----|------|
| 12シャードを順番に実行すると合計時間が長い | 手動で複数ターミナルで並列実行可能（その場合は各プロセスに独立キャッシュ） |
| 1シャード失敗時の復旧が手作業になる | シャード i の再実行スクリプトを用意 |
| 統計再計算の誤り | 10枚形で 3 シャード × 2 回実行して検証 |
| シャードサイズのばらつき | `key % numShards` は均等分布を仮定（後で測定） |
| キャッシュがシャード境界を越える | グローバルキャッシュで共有；シャード処理完了後に破棄（詳細は上記参照） |

### 実行時間に関する発見

このプロトタイプは、各シャードで `canonicalWaitCompletionGroups 3` を最初から実行して全グループを生成し、
その後で `tileMultisetKey % numShards` によりフィルタリングしている。そのため、生成処理を3回繰り返す。

### メモリ測定に関する発見

このコンテナには `/usr/bin/time` または `busybox` が存在しなかったため、スクリプトのフォールバックとして
シェル組み込み `time` が使われ、`real/user/sys` のみが記録された。したがって、今回の最大RSSは**未測定**である。
実行中のプロセスを確認した時点のRSSは約94MBだったが、これはピーク値ではない。

次回のメモリ測定では、次のいずれかを使用する：

1. GNU `time` を利用可能な環境で `/usr/bin/time -v` を実行する
2. 実行中に `/proc/<pid>/status` の `VmRSS` を定期的にサンプリングし、最大値を記録する
3. cgroup の `memory.peak` を実行前にリセットし、実行後に読む

## キャッシュエントリの圧縮方針（2026-09-11）

### キャッシュ追い出しは採用しない

キャッシュ上限を設け、超過時に一定割合を削除する方式を10枚形で試行したが、
計算途中でキャッシュを失うことによる再探索のペナルティが大きい。上限10万件・25%削除の
実行は約1時間57分経過時点でRSS約3.26GBとなり、4GiBのcgroup上限に近づいたため中断した。
したがって、ヒット率を維持するため、キャッシュエントリを途中で削除する方式は採用しない。

### 現在の値表現と問題点

現在のキャッシュ値は次の型である。

```lean
Option (List WaitCore)
```

`WaitCore` は実質的に、待ち牌、部品種別、各部品の具体的な牌種列を含む
`WaitDecomposition` である。キャッシュキーは縮小後の牌姿なので、同じキーに対する値は決定的だが、
値側では構造体、複数のリストノード、`Tile` のコンストラクタを保持している。

### 第一候補：完全なWaitCoreキー列を保存する

`WaitCore` の具体的な内容を一意に表す既存の正規化キーを公開またはキャッシュ専用関数として切り出し、
キャッシュ値を次の型へ変更する。

```lean
Option (List Nat)
```

概念的には次のようにする。

```lean
def waitCoreKey (core : WaitCore) : Nat := ...

def waitCoreKeys (cores : List WaitCore) : List Nat :=
  cores.map waitCoreKey
```

比較時には、元の手牌と縮小手牌の双方を同じキー列へ変換して比較する。
これにより、`WaitCore`、`WaitComponent`、具体的な牌種リストをキャッシュ内に保持せずに済む。

ここでは、具体的な牌種まで含むキーを使う必要がある。既存の `waitDecompositionCodes` は
部品種別へ抽象化したコードであり、具体的な牌種を忘れるため、そのまま置き換えると
現在の待ち核同値判定の意味が変わる可能性がある。ハッシュ値だけを保存する方式も、衝突時に
誤判定するため採用しない。

### 第二候補：キー列全体を1個のNatへ符号化する

`Option (List Nat)` でもリストノードは残るため、第一候補で意味論とメモリ削減効果を確認した後、
正規化済みキー列を可逆的な基数符号化で1個の `Nat` にまとめる方式を検討する。

この方式では、各キーが符号化基数の範囲内にあることを型または定理で保証する必要がある。
64ビットへ無条件に切り詰める方式ではなく、Leanの `Nat` による可逆符号化を優先する。

### 期待効果と検証方法

正確な削減量はLeanのヒープ測定で確認するが、構造体と具体牌リストを除去するため、
第一候補で1.5～4倍程度の値領域削減を期待する。これは推定であり、実測値として扱わない。

検証は次の順で行う。

1. `WaitCore` とキー列の比較が全件で一致することを確認する
2. 10枚形の可約・既約件数が既存値と一致することを確認する
3. ヒット数・ミス数が変わらないことを確認する
4. `/proc` またはcgroupの `memory.peak` で最大メモリを測定する
5. 必要ならキー列全体の単一 `Nat` 符号化を実装して再測定する

### 圧縮キャッシュ測定後の結論（2026-09-11）

キャッシュ値を `Option (List WaitCore)` から `Option (List Nat)` へ変更し、
キャッシュエントリの構造を小さくする実装を行った。4枚形・7枚形では、可約・既約件数と
キャッシュ件数が従来と一致することを確認した。

しかし、10枚形の測定では、圧縮後のキャッシュによるメモリ削減効果を確認できなかった。
実行プロセスはRSS約3.18GB、cgroup全体は4GiB上限付近に達し、`D (disk sleep)` 状態と
メモリプレッシャーが観測されたため、OOM再発を避けて停止した。

結論として、現在の10枚形実装では、キャッシュ値よりもキャッシュ以外の
`canonicalWaitCompletionGroups 3` が保持する生成済みグループ・完成情報の方が大きく、
そこだけでメモリ上限に達している可能性が高い。したがって、**キャッシュエントリの圧縮だけでは
メモリ問題を解決できない**。次に必要なのは、生成結果を全件保持しないストリーミング処理、
または生成段階からシャードへ振り分ける構造変更である。
